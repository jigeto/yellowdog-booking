# booking.yellowdog.bg — преди всяка промяна, прочети това

Този файл е за Claude (и за Димитър) — пази процеса за безопасна работа по
тази система, защото разговорите се компактират/рестартират и нищо не се
помни автоматично между сесиите. Repo: `jigeto/yellowdog-booking` (публично).

## Защо този файл съществува

На 15 окт. 2026 се оказа, че source zip-ът, върху който работеше Claude, НЕ
беше напълно синхронизиран с реалното състояние: edge функция
(`generate-consent-pdf`) се различаваше от версия, потвърдена по-рано в
същата сесия, а три SQL фикса (виж по-долу) изобщо не можеха да се проверят
от repo-то, защото живеят само в Supabase. Това правило съществува, за да не
се повтори.

## Кога ТРЯБВА данни от Supabase, кога не

**Не трябва** — промяната е чисто frontend (UI/дизайн, текстове, нов tracking
event, подредба на формуляр, стилове): repo-то стига, не питай за snapshot.

**Трябва** — провери реалното състояние първо (snapshot заявка или директен
въпрос към Dimitar), когато промяната засяга:
1. Бизнес логика/правила (капаро, отстъпки, ваучери, cancellation прозорец) —
   живее в SQL функции, не в repo.
2. Нова/променена SQL функция или тригер — виж `pg_get_functiondef` на
   функцията ПРЕДИ да я пренапишеш, иначе рискуваш да изтриеш логика,
   добавена след последния snapshot.
3. Нещо по Edge Functions (`stripe-webhook`, `generate-voucher-pdf`,
   `send-*`) — Dashboard версиите са самостоятелни copy-paste файлове, не
   истински import от repo-то; repo-то показва само намерение, не какво
   реално тече.
4. Схема на таблица (нова колона, enum, constraint) — провери
   `information_schema.columns` първо, не гадай тип/име.
5. Диагностика на жив бъг — винаги реални данни от базата, никога
   предположение.

## Архитектурен капан №1: три различни "истини"

Системата има **три отделни места**, които могат да се разминат:

1. **GitHub repo** (`jigeto/yellowdog-booking`) — frontend source (`src/`).
2. **Supabase база** — SQL функции/тригери/таблици, управлявани **директно
   през Dashboard SQL Editor**, НЕ през repo миграции. Няма `supabase/migrations/`
   папка с история — промяна по база = изпълнена SQL заявка, нищо повече.
   Ако никой не е записал кое точно е пуснато, няма как да се провери освен
   да се прочете текущото определение на функцията (`pg_get_functiondef`).
3. **Supabase Edge Functions в Dashboard** — всяка функция (`generate-voucher-pdf`,
   `stripe-webhook`, `send-voucher-email`, `generate-consent-pdf` и др.) е
   **самостоятелен copy-paste файл в Dashboard**, не истински import от
   `supabase/functions/` в repo-то. Промяна в споделен код (напр.
   `_shared/voucher-pdf.ts`) трябва РЪЧНО да се копира в **всяко** място,
   което го ползва — пропускането на едно от тях е най-честият източник на
   разминаване. Виж конкретния пример по-долу (ваучер PDF).

**Правило:** repo-то (или архив от него) показва само точка (1). За (2) и (3)
трябва РЕАЛНА проверка всеки път, не предположение.

  конфликт на идентификатори при копиране на споделен код (напр.

  Суперхостинг. Edge Functions: ръчен copy-paste в Dashboard за всяка
  функция поотделно.
